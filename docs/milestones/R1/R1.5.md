## Objective and scope

R1.5 creates one enforceable, versioned, default-deny boundary between files
that the project has approved for a distribution profile and material that is
commercial, unreviewed, historical, development-only, or unknown. It adds the
manifest, a standard-library Python validator, actual staging-tree checks,
notice reporting, tests, and validation-runner jobs.

No C engine, gameplay, renderer, WL6 parser, `CA_StartupWithContent()`, PK3,
Workshop, or runtime content-loading code changed. The manifest answers “may
this file enter this release profile?” The future R2 runtime manifest will
answer “how does the engine identify and load this resource?”

## Manifest contract

Top-level `schema_version = 1` is mandatory. `[distribution]` names the policy,
states its purpose, and must set `default_policy = "deny"`. `[limits]` bounds
the manifest and staging walk. `[profiles.<name>]` defines a release profile
and its required approved asset IDs.

Each `[[asset]]` has a stable ID; one exact `path`, a homogeneous exact `paths`
set, or a directory `prefix`; type, origin, creator, licence state,
redistribution state, evidence, profiles, attribution flag, and notes. A prefix
is a normalized POSIX relative path ending in `/` and matches descendants only.
Selectors may not overlap. Paths are case-folded to reject collisions.

Policy states are exact and fail closed:

| State | Meaning for `original-standalone` |
| --- | --- |
| `approved` | May be staged only at its exact registered path and with its registered SHA-256 |
| `prohibited` | Explicitly rejected; used for commercial/external legacy data |
| `pending-review` | Evidence or rights remain unresolved; never treated as approved |
| `development-only` | Useful in the source/development tree but excluded from standalone payloads |

Every file-specific approved entry requires an exact SHA-256, a supported
licence state, existing provenance evidence, and complete notice metadata when
attribution is required. The notice path must itself resolve to an approved
exact asset for the profile. When an attributed asset is actually staged, that
notice asset must also be staged and pass its own registered SHA-256 check; a
manifest-only notice entry does not satisfy the release gate.

Approval accepts the reviewed SPDX identifiers `GPL-2.0-only`, `MIT`, `Zlib`,
`CC0-1.0`, `CC-BY-4.0`, and `OFL-1.1`. Adding another identifier requires an
explicit validator review rather than accepting arbitrary SPDX-looking text.
`NOASSERTION`, proprietary-commercial, pending-review, and historical-unverified
states may document non-approved entries but can never grant approval. A digest
proves file integrity only; it does not prove authorship, permission, or legal
validity.

## Commands and behavior

```sh
python3 tools/validate_distribution.py check
python3 tools/validate_distribution.py inventory
python3 tools/validate_distribution.py notices --profile original-standalone
python3 tools/validate_distribution.py verify \
  --profile original-standalone --root dist/staging
python3 tools/validation/run.py R1.5
```

`verify` walks the actual root without following symlinks. It rejects absolute,
drive-qualified, traversal, mixed-separator and overlapping manifest paths;
symlinks; special files; unreadable files; unexpected empty directories;
case-insensitive collisions; unknown, prohibited, pending-review and
development-only files; missing required files; size/count limit breaches;
hash mismatches; a staged attributed asset whose approved notice file is absent
or fails its own hash; and a file whose device/inode/size/mtime changes before
or during its streaming hash. It performs no deletion or mutation.

An unlisted renamed proprietary file is rejected by default deny. The validator
does not inspect bytes to determine copyright origin and cannot prove that a
renamed file is or is not commercial material. Policy review and provenance are
still required.

## Adding an original sprite, texture, sound, or other asset

1. Create or import the asset without placing uncleared commercial data in Git.
2. Determine and record its real origin and creator.
3. Identify the applicable licence or written permission; use an unresolved
   state when this is not established. Approval requires a reviewed identifier;
   current original-asset options include `CC0-1.0`, `CC-BY-4.0`, and
   `OFL-1.1` where their actual terms and asset type apply.
4. Add durable provenance evidence to the repository.
5. Register the exact path as `pending-review`; do not infer approval from Git,
   a filename, a generated/AI origin, or a successful build.
6. After review, change the entry to `approved`, compute its SHA-256, and record
   attribution/notice requirements and the approving release profile.
7. Generate and review `notices`, stage the real candidate package, and run
   `verify` against that staging root.
8. Re-review any content change; a changed approved file fails its pinned hash.

The entry records the project’s clearance decision. It is not independent proof
that redistribution is lawful.

## Known limitations and blockers beyond R1.5

- Historical `WOLFSRC` binaries, tools, objects, artwork, `gamepal.inc`, and
  `GFXV_WL6.h` remain pending review. A formal licence review is still required
  before broad source or binary distribution decisions.
- The active-source GPL basis is a project statement, not an independent legal
  opinion. GPL source-offer/compliance details remain a release responsibility.
- SDL is external and its notice is not tracked as an approved payload asset.
  If a future package bundles SDL, add its reviewed notice and exact package
  inputs before approval.
- The current approved payload is notices only. R3 must create and clear
  original content; R8 must approve exact binaries/platform dependencies and
  verify complete staged packages.
- Validation was run on Linux. Cross-platform release validation remains R8.
- Default deny blocks renamed unlisted files but is not content-recognition or
  copyright-detection technology.

These are not failures of the R1.5 enforcement mechanism, but they block any
claim that an original standalone game is currently ready for distribution.

## R2 handoff and rollback

R2 may consume the validator as a reusable “may this resource be packaged?”
decision, but must not add runtime resource IDs, dependencies, maps, or loader
semantics to this manifest. New loose/package/Workshop content starts unapproved
for official distribution. R2.3 owns the distinct versioned runtime content
manifest.

Rollback is removal of the R1.5 manifest/tool/tests/runner registration and the
two documentation updates. No engine state or content format migration is
required. The next exact verification command is:

```sh
python3 tools/validation/run.py R1.5
```
